## Protocol — known from prior art, MUST VERIFY on this unit
Family (ACiQ + Zokop projects, both proven on sibling hardware):
- Frame: `A5 01 <link> <type> <counter> 00 00 <len> <crc16hi> <crc16lo> <payload...>` @ **115200 8N1**, len includes the header, big-endian CRC field.
- `<type>`: `0x21` report/command/clock, `0x23` ACK (echoes counter).
- Payload headers at bytes [10:12]: `0C 0C` = state report, `0A 0A` = command, `0D 0D` = clock. Clock requests seen: `10 10`, `80 10`, poll `26 26`.
- **CRC-16/XMODEM** (poly 0x1021, init 0, MSB-first), two documented variants:
  - **"hole"** (ACiQ): whole frame with bytes 8–9 **removed, not zeroed**. Verified on 105 frames, lengths 12–90.
  - **"prefix"** (Zokop): header bytes 0–7 only.
  - Our listener counts both in parallel; the capture decides which one this unit uses. **RESOLVED 2026-10-20: ACiQ-hole variant — 3,974 verified frames, 0 bad, 0 prefix.**
- Records start at offset 13: `<id> <val>` pairs where the byte BEFORE each id is a **namespace** selector (`00` plain field, `02` parameter); last record has no trailing separator. Widths: narrow = 3 bytes total; wide = `<id> 00 00 <hi> <lo>` (6 bytes) for ids {0x02,0x03,0x5C,0x60,0x64,0x65,0x72,0xC0} + unidentified wide {0x95,0xBD,0xBE,0xBF}; namespace-0x02 params: fid 0x21/0x22/0x27/0x64 → 4 data bytes, fid 0x24/0x25 → 1; ids 0x38/0x39 are length-prefixed lists (`<fid> <len> <data...>`).
- **Setpoint** = trailing signature: frames end `02 27 00 00 00 <degF>`.
- **Verified field map (ACiQ hardware; expect most to carry over)**:
  - narrow: `01` power, `05` fan speed (7 steps + auto), `0E` h-louver, `11` v-louver, `12` mode (0 auto/1 cool/2 dry/3 fan/4 heat), `13`+`DF` eco pair, `15` health/ionizer, `1E` display light, `22` sleep (enum 0–3), `25` beep, `27` drying, `73` fan-auto flag, `2D` generator-mode limiter
  - wide (centi-C unless noted): `02` setpoint, `03` room temp (unprompted ~every 60 s), `5C` indoor coil, `60` outdoor, `64` input watts, `65` compressor actual %, `72` fan %, `C0` compressor target %
- **Behavior notes**: the mainboard transmits autonomously even with no module attached (ACiQ: "AC powered alone, no module → RED active"); unACKed boards retry aggressively (~75 frames/min vs ~3.5 with ACKs); silence is abnormal (dongle runs on standby power).
- **NOT** Tuya 55 AA, NOT Midea AA@9600 — the WBR1's TCL Home firmware matches nothing public; 115200 was measured empirically by ACiQ (2347/2347 pulses).

## D+ (white) incident — 2026-10-20 (field experiment, node live)
Field-tested nets 7/8 (**D+ white → B2, A2 → D6**) on the running system; Tuya OUT throughout. Watcher timeline (`/tmp/opencode/ac-bus-watch.log`):
- **Phase 1** (D+→B2 **and** A2→D6): AC kept running normally, but the ESP went **offline in HA** (~18:42 UTC). Prime suspect: something on the mainboard side drives D+ → push-pull contention with our TX + 5V backfeed through the TXS0108E (it passes the higher rail) into non-5V-tolerant GPIO16.
- **Phase 2** (D+ still on B2, A2 disconnected from D6): node back **online but the bus produced raw bytes only — zero CRC-valid frames** (18:54–18:57: rx 0→261, frames=0). A passive high-Z shifter input should not disturb mainboard transmissions on D-; leading suspects: (a) our "B2" pad actually bridges into channel 1's B1 (the live D- tap net), injecting D+'s signal into our own RX decode; (b) the white wire is coupled to / driven by something on the mainboard side we don't understand; (c) phase 1 left the mainboard latched in an error state that only cleared on full disconnect.
- **Phase 3** (D+ removed from B2): **full recovery** — real decodes again within minutes (19:08–19:14, frames climbing, normal UNMAPPED queue incl. `21=1600(60.8F)`, `22=3100(87.8F)`). User then **unplugged the ESP when leaving the house** (offline from ~19:16 onward is deliberate, not a fault).
**Verdict: D+ (white) is OFF-LIMITS on this unit until characterized.** Do not drive it; do not keep re-testing. And our color labels are unverified guesses — in ACiQ's harness **white = GND** (Red=AC-TX, Black=mod-TX, Yellow=+5V). Wire identity must be established by measurement/capture, never color (procedure below). **RESOLVED 2026-10-20 (final metered map):** white really is **GND** — it was never a data wire; the incident was our own miswiring (true GND on a B-side data pad → −5 V out-of-spec on the shifter), not a hostile wire. ACiQ's harness colors match nothing about ours either — only the metered map in the wiring doc is authoritative.

## ACiQ architecture findings — 2026-10-20 (repo mirrored to `aciq-reference/`)
- Their capture methodology proves the protocol is **dual-wire full-duplex**: "8 MSa/s capture, both directions" — one wire = mainboard→module, the other = module→mainboard. The module→mainboard direction (ACKs, commands, clock answers) rides a **separate wire we have not identified yet** — and our "D+ (white)" candidate just proved hostile in the field.
- Their takeover build: UART#1 = RX-only tap on the mainboard→module wire; UART#2 = **TX + RX (echo tap) on the module→mainboard wire** — one added wire for TX, echo verification free off the same line. `Transmit Enabled` interlock is RESTORE_DEFAULT_OFF — exactly our `TX Armed` design.
- Module frames we now have byte-exact references for (`esphome/aciq_tx.h` + `captures/reference-frames.txt`): ACK `A5 01 <link> 23 00 <counter@5> 00 0C <crc-hi> <crc-lo> 80 <ptype>` (ptype: 0x0C report / 0x0A command / 0x0D clock; turnaround ~49-50 ms); clock answer `A5 01 00 23 .. 80 10 <unix BE32 @12..15> FB`; RSSI heartbeat (`02 64` param, int32 dBm, ~1/min); commands = report-shaped type **0x21** with payload header `0A 0A`, records `<00><id><val>` / wide `<00><id> 00 00 <hi><lo>` / param ns `<02><id> 00 00 00 <val>` (param **0x27 = setpoint °F display**; wide 0x02 = centi-°C at 50 counts/°F: `centi_c = 2700 + (degF−81)×50`, clamp 1600/3100); mode field **0x12** (observed values 0,1,2,4,3 cycled by five presses), fan **0x05** + 0x72 percent + 0x73, power **0x01**, room temp **0x03** centi-°C ~60 s.
- **Cross-check result: our 2a ACK is byte-for-byte identical to `aciq_tx.h ack()`. Our clock answer was WRONG** (it mimicked the mainboard's own 0D 0D time-broadcast, type 0x21) — **fixed 2026-10-20 to the verified `0x23`/`80 10`/unix@12..15/`FB` layout and recompiled clean** (config_hash 0x28e960a4). Next OTA ships that image.

- **Red = +5 V (VBUS)** — confirmed: it's wired to the shifter's B rail (VCCB).
- **White ("D+") = 5 V** — this is an **idle-high, pulled-up data line**, NOT a power rail. By elimination (red=+5V, black=GND, green=AC-TX) **white = mod-TX (module→mainboard) = our TX target.**
- **Green ("D-") = AC-TX** (decodes `0x21` reports + clock reqs); metered 0–1 V — odd for an idle-high line, keep an eye on it but it's proven to carry valid data.
- **Black = GND** (by elimination; verify ≈0 V).
→ So the D+ incident was almost certainly an **electrical/wiring fault on our side** (5 V backfeed through the bidirectional shifter into non-5-V-tolerant GPIO16, and/or a bridged pad on channel 2) — **not** a wrong-wire or power-rail problem. ACiQ drives their mod-TX line through a spare channel of the same shifter class successfully, so the topology is sound; find what specifically went wrong on ours (inspect ch-2 for bridges, verify VCCA=3.3V rail is solid, consider a different free GPIO if D6 got damaged).

## Decisions (with reasoning)
1. **Branch B = UART takeover** (vs A "midea_ac_lan rebrand theory" — dead, WBR1/TCL Home confirmed; vs C "IR blaster" — fallback only).
2. **No USB splitter / never run Tuya + listener driving in parallel** — a Y-cable would put both modules' data lines in parallel = push-pull contention risk. Receiver-only taps make "Tuya in" or "Tuya out" safe either way; Session 1 default is Tuya OUT (cleaner).
3. **Phase 1 node = SLWF-01 Pro** (flashed with our listener; plugs into the AC port exactly where Tuya sat — no soldering, no shifter because the board does the level conversion on-board; powered from the AC port's VBUS only, never simultaneously by Type-C). **Final node = XIAO ESP32C6 + level shifter** (purchased 2026-10-20; bus expected 5V per ACiQ's measurement; meter first). **Permanent power = harness VBUS on the XIAO 5V pin** — USB-C is test-period only, one source at a time (backfeed rule); after conversion, updates are OTA only. The SLWF ran hot in the sealed cabinet once (incident above) — acceptable for a temporary Phase 1 node, watch its temperature.
4. **Session 1 is receive-only until framing + CRC variant are verified on this unit** — the listeners never transmit (C6 build has no tx_pin at all; SLWF build configures TX only to match the board's factory idle-high state and never writes it), so they physically cannot cause a regression.
5. **No WAGO splices.** The C6 tap = the extension cable's free USB-A end into a passive breakout (Dreame Breakout's USB-A socket, or the $5 DIP board). Fully reversible, nothing cut. RYLS135 is the Path A probe only — as a USB endpoint device it can never sit inline in the harness.
